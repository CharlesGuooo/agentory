# 设计

## D-S1 · 砍掉 D-7 里的文件监听

D-7 原本写了「源文件变了 + 静默 30 秒 → 重新摘要」。**本变更把它砍掉**，理由是 D-7 自己那句话：

> 开在 tab 里的会话你看得见，不需要摘要；摘要的价值全在你看不见的那些。

监听盯的正是**你看得见的那些**，与它自己的论证矛盾。

改为：**下次批量跑到它时，按 `lastActivity` 判断过期再重摘**。
过期的**照常显示** —— 旧摘要也比没有强。

净效果：少一个 watcher、少一套防抖、少一类「摘要正在后台变化」的竞态。

## D-S2 · 工具输出靠**结构**挡住，不靠黑名单

尾部实测 **56% 是工具行**，而**用户的源码就藏在 `tool_result` 里**。

挡它的方式不是列一张 `tool_result` / `tool_use` 的黑名单，而是**只取 `type === "text"` 的片段**：

```ts
.filter((p) => p["type"] === undefined || p["type"] === "text" || p["type"] === "input_text")
```

工具片段在五个 agent 里都是**别的类型**，取不到 text 就成了空消息，自然被丢掉。

**为什么必须是结构规则**：`add-favorites` 里那张注入白名单漏掉了 grok 的 `<user_query>`
和 codex 的 `<recommended_plugins>`。白名单挡的是「我知道的」，结构规则挡的是「这一类」。

对应的断言不是「不含 `tool_result` 这个词」（我们自己的会话里就有人在讨论这个词），
而是**从真会话的原始尾部抠出一段工具输出的实际内容，断言它没出现在载荷里**。

## D-S3 · 尾部必须渐进扩大地读

D-7 没预料到的坑：**实测单条 `tool_result` 最大 361 KB。**
读一个固定的 64 KB 尾部窗口，**可能整个窗口都落在一条工具输出里，一条纯文本都拿不到** ——
那样摘要就只剩首条 prompt，等于白做。

```
64 KB → 256 KB → 1 MB → 4 MB（硬上限）
```

拿够就停；窗口已覆盖整个文件也停。**绝不整文件读**（本机存在 195 MB 的单会话）。

实测尾部命中率：**436/437**（claude 72/72、codex 64/65、opencode 166/166、pi 14/14、grok 120/120）。

## D-S4 · 用结果本身表示进度，不建作业队列

沿用 D-13。续做 = 「列出目标范围里还没有缓存的，接着做」，进度 = `已缓存 / 目标总数`。
天然幂等、天然可续、崩溃安全、零额外状态。

**串行**跑（复用 `restoreSerially` 的形状）——
不是因为 API 限流（v4-flash 允许 2500 并发），是因为**用户随时可能关掉应用**：
串行时「已经写进缓存的」永远是一个前缀，续做逻辑因此不需要任何额外状态。
每成功一条就落盘，已经花过的钱不能丢。

## D-S5 · 「看看会发送什么」是本变更的核心，不是附加功能

D-8 的整套理由是「不会在用户不知情时把源码发出去」。
`summary:preview` 把那句话从**承诺**变成**可验证的事实**：
展示的就是 `runJob` 会发的**同一段文本**（同一个 `renderPayload`），不是另写一份说明。

## D-S6 · API key 的存放

1. `DEEPSEEK_API_KEY` **环境变量优先** —— 不想让密钥落盘的人有一条不落盘的路
2. 否则存 `deepseek.key`，用 Electron `safeStorage` 加密（Windows 走 DPAPI，密文绑定当前账户）
3. **不进 `settings.json`** —— 那份文件用户会自己打开手改
4. 解不开（换机器 / 换账户）就删掉让用户重填，而不是反复报错

## 过程中发现的两个**既有**缺陷（都不是本变更引入的）

### 一、opencode 的库被锁住时，166 条会话会整块消失

实测（并发读同一个库时可复现）：

```
[opencode] 扫描失败：database is locked
  opencode     0 个   cwd    0/0      原生标题 0
```

`scanOpenCode` 抛出异常 → `scanAll` 记一条 problem → **用户看到 opencode 那一栏空了**，
没有任何解释。库是 WAL 模式，锁是毫秒级的。

修法用 SQLite 自己的机制，不手搓重试：

```ts
new DatabaseSync(dbPath, { readOnly: true, timeout: BUSY_TIMEOUT_MS })
```

修复前 2 次复现 1 次，修复后连跑 5 次全部 437 条。

### 二、打开历史弹窗要等 1 秒以上

`sessions:list` 在「打开历史」的路径上。**冷进程首次扫描 437 条实测 1.1–1.8 秒。**

（同一进程里第二三次是 0.75 秒 —— 那是热数据，不代表用户感受。）

本变更**没有修这个**，它是 D-4「不建索引数据库」的既有代价，
修它要重新讨论 D-4 而不是顺手优化。已记进 DESIGN.md 待办。

相应地，`real-machine.test.ts` 里那条性能测试改了断言对象：
原来断言「总耗时 < 1 秒」，而本机语料每天都在长（开发这个应用本身就在往里写会话），
HEAD 自己就已经跑到 941 ms —— 那条测试早晚会在某天无关的提交上翻红。
改为断言**单条成本没有数量级回归**，并加 `npm run perf` 单独跑干净数字。

> 它今天真的抓到了一次 **15 倍**的回归：opencode 的 SQL 窗口从 48 提到 480，
> 每条会话 1.2 → 28.3 ms，全量扫描 0.67 → 10.2 秒。
