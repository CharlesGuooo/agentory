## Context

索引层（`add-session-index`）已经产出 437 条会话记录，含真实 cwd 与 agent 原生 id。
本变更把它们变成「点一下就能回到那个对话」。

用户问过「先接进侧栏、有 bug 再修，还是一次做好」。两者都不取 ——
**「437 条怎么显示」不是 bug，是缺决策**，而 D-5 / D-8 已经把它答了：
侧栏是工作集，历史走独立视图且默认不扫。靠上线去发现这类问题等于用打补丁做设计。
所以本次是一个**纵切片**：小到 TDD 是真的，完整到能验收，动手前规格已定。

## Goals / Non-Goals

**Goals:**
- 五套恢复命令，纯函数，严格 TDD
- 历史视图：可搜索筛选，从中恢复一条
- 真机验收：恢复一个真实会话，**看到历史对话回来**

**Non-Goals:**
- 工作集、持久化、批量恢复、摘要
- 侧栏的默认行为一律不动

## Decisions

### D-R1 · 恢复命令是纯函数，与进程启动分离

`resumeCommand(session) → { command: string; args: string[] }`。
不碰文件系统、不起进程 —— 五个 agent 的差异全部落在一个可穷举测试的函数里。

启动交给 `terminal-host` 已有的 `spawn`（它已支持 `args` 与 shim 解析）。

### D-R2 · 拒绝「不存在就创建」的参数，这是硬约束不是偏好

`pi --session-id` 与 `grok --session-id` 在会话不存在时**静默新建**。
用它们恢复，失败时不报错而是给一个空会话 —— 用户以为历史回来了。

**静默失败比报错危险得多**，所以规格里把它写成了否定性要求，并配了两条专项场景。
`docs/research-notes.md §3.3` 对 grok 的记载（`--session-id`）就是错的，本次一并修正。

### D-R3 · cwd 不可用时拒绝恢复，不做任何回退

`cwdExists === false`（本机 35 条）或 `cwd === null` → 拒绝，并说明原因。

**不回退到用户主目录或项目根**：agent 的会话按目录划分，
在错的目录下恢复轻则找不到、重则在别的项目里开出一个新会话。
错误消息比一个"看起来成功了"的错误会话有用得多。

### D-R4 · 搜索与筛选是纯函数，界面只负责渲染

`filterSessions(sessions, { text, agents })` 独立于 DOM，可严格 TDD。
这是本变更里 UI 部分唯一能被自动化测试覆盖的地方 —— 其余靠冒烟 + 人眼。

### D-R5 · TDD 的力度按层分配，且如实说明

- **`resume.ts` / `filter.ts`**：先写测试、看它红、再实现
- **历史视图的 DOM**：无自动化测试。理由同 `add-app-shell` ——
  `docs/research-notes.md §9` 明确列了「不搭一套用不上的前端测试设施」。
  靠命令行冒烟 + 用户真机验收

**不假装 UI 也被测了。**

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| agent 升级改掉 resume 语法（grok 仍在 beta；codex 今天刚从 0.146 升到 0.147） | 命令表集中在一个纯函数里，改一处即可；真机验收会立刻暴露 |
| 恢复成功但对话没回来（静默新建） | D-R2 的两条否定性要求；真机验收标准是**看到历史对话**，不是"进程起来了" |
| 437 条一次性渲染卡顿 | 先直接渲染并实测；真慢再谈虚拟列表，不预先优化 |
| 索引在历史视图打开时已过期 | 每次打开重扫（339 ms，D-4 已定不建缓存） |

## Open Questions

- **（实测新增）恢复一个正在运行的会话会怎样？** 实测：对当前活着的 claude 会话执行
  `--resume <id>`，它只吐终端能力协商序列（`ESC[<u` / `ESC[>0q`）就没下文，**不渲染**。
  产品上该怎么处理还没定 —— 是禁掉、是提示"该会话正在运行"、还是允许并排两份。
  真机验证的测试目前用「跳过最后活动在 1 小时内的会话」绕开它。
- 恢复后是否该把该会话自动加入工作集？倾向**不**自动加 ——
  工作集是用户策展的（D-5），自动加会让它悄悄膨胀。留到工作集那一刀再定。
