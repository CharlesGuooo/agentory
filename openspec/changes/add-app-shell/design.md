## Context

`prototype-terminal-fidelity` 交付后，应用是一个占满窗口的裸终端 + 两个切主题的快捷键。
用户看过 Claude 桌面版的截图后提出对标要求，并明确：**只模仿 UI 的现代化风格，配色不动**
（五套主题已在 D-14 与附录 A 定稿）。

用户还提出过一个技术疑问 —— 「你用的窗口是不是技术栈过时了」。
澄清：观感差距与框架无关，Claude 桌面版同属 web 技术栈的桌面壳。
差别在于**它藏掉了系统标题栏、自己画了一条**，而我们当时用的是系统默认那条。

## Goals / Non-Goals

**Goals:**
- 把 D-1 的形态（左 explorer + 顶 tab）立起来
- 补齐 `theme-system` 缺失的那一半：界面上能选主题，且能看出各套的观感
- 观感对齐 Claude 桌面版：自绘顶栏、侧栏比主区亮一档、细边框、圆角卡片、大留白、近乎无彩只留一个强调色

**Non-Goals:**
- 多会话、工作集持久化、批量恢复、历史搜索、会话摘要 —— 都是后续独立的能力
- 不改任何配色值
- 不做主题取色器（D-14 已定：自定义走 JSON 文件）

## Decisions

### D-S1 · 原生窗口控件贴进自绘顶栏，而不是自绘三个按钮

用 `titleBarStyle: "hidden"` + `titleBarOverlay`。系统把真正的最小化/最大化/关闭画进我们的顶栏。

**理由**：自绘按钮要自己实现贴边、Snap、双击最大化、无障碍标签、以及各种 Windows 版本的行为差异 ——
那是把平台已有的东西重做一遍。用 overlay 只需给两个颜色。

**代价**：顶栏高度在主进程和 CSS 两处各写一次，不一致就会错位。已在两处互相注明。

### D-S2 · 变体解析在渲染层，所以窗口控件的颜色由渲染层回传

主进程知道主题列表和 mode，但「当前该用 dark 还是 light 组」是渲染层算的（`resolveVariant`）。
与其在主进程重算一遍，不如让渲染层在应用主题后把两个颜色回传（`window:overlay`）。

**被否决的替代**：把变体解析搬到主进程 —— 会让渲染层每次都要问主进程要颜色，多一次往返。

### D-S3 · 界面上只显示真实数据

侧栏和标签页现在各只有一条，因为应用确实只起了一个会话；摘要位显示「摘要功能还没做」。

**理由**：用假数据填满界面能让截图好看，但会掩盖「多会话和摘要都还不存在」这个事实，
也会在真数据接进来时暴露一堆没考虑过的情况。规格里把这条写成了硬要求。

### D-S4 · 样式表不出现硬编码色值

全部走 `--c-*`。唯一例外是关闭按钮悬停的红（`#e81123`），那是 Windows 的约定色，
跟着主题变反而不对。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| 顶栏高度两处定义，改一处忘另一处 → 原生控件错位 | 两处互相注明；规格里写成一个场景 |
| `titleBarOverlay` 是 Windows/macOS 特性，Linux 上行为不同 | 本项目是 Windows 专用（DESIGN.md §1），不在范围内 |
| 侧栏占掉 236px，终端可用列数从 164 降到 135 | 已实测确认布局生效；将来侧栏应可折叠，但那是新需求，现在不做 |
| 先实现后补规格，规格可能只是描述现状而非约束 | 已在 proposal 顶部标注流程偏差；规格里刻意写了几条**否定性**要求（不放假数据、不硬编码颜色），它们约束的是将来 |

## Open Questions

- 侧栏能否折叠 —— 未讨论，等多会话落地后再看是否需要
- 标签页数量多时如何处理（滚动？溢出菜单？）—— 目前只有一个会话，不预先设计
