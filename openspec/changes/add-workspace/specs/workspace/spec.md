## ADDED Requirements

### Requirement: 工作集成员资格只由显式动作改变

工作集 SHALL 只在用户显式新建会话、从历史恢复会话、或结束会话时发生变化。
SHALL NOT 因为任何自动行为（扫描、索引、进程退出）而增删成员。

这是 D-5 的核心：**`active` 与 `running` 是两个正交概念**。
会话跑没跑是运行时属性，在不在工作集是用户的策展结果。

#### Scenario: 新建会话加入工作集

- **WHEN** 用户通过选择器新建一个会话
- **THEN** 该会话成为工作集成员

#### Scenario: 从历史恢复也加入

- **WHEN** 用户从历史视图恢复一条会话
- **THEN** 该会话成为工作集成员
- **AND** 理由：这同样是用户的显式动作

#### Scenario: 进程退出不改变成员资格

- **WHEN** 某个工作集成员的子进程退出
- **THEN** 它仍是工作集成员，只是状态变为「已停」
- **AND** 这正是「关机后工作集完好无损」得以成立的原因

#### Scenario: 结束会话才移出

- **WHEN** 用户对某个成员执行「结束会话」
- **THEN** 它被移出工作集
- **AND** 其子进程被终止（若在运行）

### Requirement: 工作集持久化

工作集 SHALL 在每次变化后写入磁盘，并在应用启动时读回。

#### Scenario: 重启后成员完好

- **WHEN** 工作集有若干成员，应用被关闭后重新打开
- **THEN** 全部成员仍在工作集中
- **AND** 全部处于「已停」状态

#### Scenario: 记录足以恢复的信息

- **WHEN** 一个会话加入工作集
- **THEN** 记下 agent、会话 id（可为空）、真实工作目录、加入时间
- **AND** 这些足以在重启后生成启动命令，无需重新扫描索引

#### Scenario: 新建的会话没有 id

- **WHEN** 用户在 agentory 里新建一个会话
- **THEN** 该条目的会话 id 为空 —— agent 的 id 是它自己生成并写进会话文件的，
  spawn 那一刻拿不到
- **AND** 这类条目靠「继续该目录下最近的会话」恢复，而不是靠精确 id

### Requirement: 启动命令按是否知道会话 id 分两种

系统 SHALL 在知道会话 id 时精确恢复该会话，在不知道时使用
agent 的「继续该目录下最近的会话」参数。

| agent | 知道 id | 不知道 id |
|---|---|---|
| claude | `--resume <id>` | `-c` |
| codex | `resume <id>` | `resume --last` |
| opencode | `--session <id>` | `-c` |
| pi | `--session <id>` | `-c` |
| grok | `--resume <id>` | `-c` |

#### Scenario: 从历史恢复进来的用精确 id

- **WHEN** 某条目的会话 id 已知
- **THEN** 生成精确恢复该会话的命令

#### Scenario: 新建的用「继续最近」

- **WHEN** 某条目的会话 id 为空
- **THEN** 生成该 agent 的「继续该目录下最近会话」命令
- **AND** 已知代价：若用户在同一目录用 agentory 之外的方式又开过会话，会接到那一个

#### Scenario: 两种情况都不使用「不存在就创建」的参数

- **WHEN** 生成任何一种启动命令
- **THEN** 命令中不出现 `--session-id`

#### Scenario: 文件损坏不阻止启动

- **WHEN** `workspace.json` 不是合法 JSON 或结构不符
- **THEN** 应用以空工作集启动并记录告警
- **AND** 不崩溃、不静默覆盖用户原文件

#### Scenario: 首次启动

- **WHEN** 文件不存在
- **THEN** 工作集为空，且这不是错误

### Requirement: 会话 id 是工作集的主键

同一个 `(agent, sessionId)` SHALL 在工作集中最多出现一次。

#### Scenario: 重复加入不产生副本

- **WHEN** 用户恢复一条已在工作集中的会话
- **THEN** 工作集中该条目不重复，仅其运行状态更新

### Requirement: 批量恢复是串行的

恢复多个会话时，系统 SHALL 一次只起一个，前一个起完再起下一个，
SHALL NOT 并行启动。

依据实测负载：8 个 claude 会话会拉起约 15 × 8 个 MCP 子进程，单机破百（`docs/research-notes.md` §10）。
并行恢复 6 个 = 瞬间近百进程，外加 6 份上下文重载的开销。

#### Scenario: 串行且带进度

- **WHEN** 用户勾选 6 个会话并确认恢复
- **THEN** 它们被依次启动，界面持续显示已完成数与总数
- **AND** 期间用户可以正常操作已经起来的会话

#### Scenario: 其中一个失败不中断其余

- **WHEN** 某个会话恢复失败（例如工作目录已被删除）
- **THEN** 记录该失败并继续恢复剩下的
- **AND** 结束后汇总说明哪几个没成功、为什么

### Requirement: 恢复默认不自动执行

批量恢复 SHALL 默认只把会话放回工作台而**不启动进程**，
由用户再做一次确认才真正启动。

**本条是 D-12 的精神实现，字面做法已被否决**：D-12 原写「把命令打进终端但不回车」，
那需要先起一个 shell 再往里打字 —— 那个 tab 托管的就成了 shell 而非 agent，
pid、退出码、状态追踪全部对不上。

#### Scenario: 未启动状态可见且可解释

- **WHEN** 一个会话被放回工作台但尚未启动
- **THEN** 它以「未启动」状态出现，并显示将要执行的完整命令
- **AND** 用户能看出点下去会发生什么，而不是面对一个空白终端

#### Scenario: 一次确认即启动

- **WHEN** 用户对某个未启动的会话确认启动
- **THEN** 该会话按其恢复命令在真实工作目录下启动

### Requirement: 不跨应用重启续做恢复

批量恢复 SHALL NOT 在应用重启后自动继续未完成的恢复。

已恢复的会话是本应用的子进程，应用关闭它们就没了 —— 「续做」没有意义。
（这与扫描/摘要那类作业不同，那些的产物在磁盘上，见 D-13。）

#### Scenario: 中途关闭应用

- **WHEN** 批量恢复进行到一半时应用被关闭
- **THEN** 下次启动不自动继续，而是照常展示工作集与恢复入口
